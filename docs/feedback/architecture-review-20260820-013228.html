Candidate 01 · library scan depth

Deepen the ROM survey into one scan module

Strong

Files / modules

  • LibraryManagerViewModel.kt:532-608
  • LibraryRescanCoordinator.kt:30-158
  • ScanSourceResolver.kt and LibraryReconciler.kt
  • the two existing test modules for manual and triggered scans

Problem

The ScanSourceResolver is shared, but the important scan loop is not. Both callers rebuild the existing-path set, collect every source, upsert new games, union presentRomPaths, propagate errors, reconcile Missing rows, and record counts. The ViewModel adds UI state on top; the coordinator repeats the policy headlessly. The comment in the coordinator openly describes the duplication.

Solution

Deepen a library scan module that owns the full survey and reconciliation policy. Keep UI message/state mapping in LibraryManagerViewModel and trigger timing in LibraryRescanCoordinator; both callers consume the same scan result.

Candidate 02 · theme depth

Deepen theme application from file plumbing into a theme module

Worth exploring

Files / modules

  • PfpThemeStore.kt — 348 lines
  • ThemesSettingsViewModel.kt and ThemesSettingsScreen.kt
  • PfpThemeCodec.kt, SafeMedia.kt, and XMB preference readers
  • PfpThemeStoreTest.kt — Robolectric + real files + DataStore

Problem

PfpThemeStore owns library indexing, SAF reads, bounded decoding, bitmap lifecycle, sidecar generation, bundle persistence, export naming, icon extraction, layout sanitization, wave-style mapping, and DataStore cascade writes. The theme settings module and XMB module also repeat preference-key contracts. The implementation is deep, but its interface exposes a broad set of unrelated operations and the tests must reconstruct Android storage to reach the real behavior.

Solution

Deepen the theme module around two cohesive concepts: bundle/library ownership and applied-look ownership. Keep SAF and file access behind adapters, make the applied-look calculation local, and let settings render state rather than know cascade key details. Do not choose the final interface before grilling.

Candidate 03 · trigger seam

Deepen rescan triggers into one Android adapter path

Worth exploring

Files / modules

  • MainActivity.kt
  • MediaMountReceiver.kt
  • UsbDisconnectReceiver.kt
  • LibraryRescanCoordinator.kt

Problem

Three Android entry points repeat Hilt EntryPoint lookup, an IO coroutine scope, logging, and exception swallowing. The coordinator owns throttle/debounce/single-flight policy, but mutable trigger state is still spread across entry points and its token/time fields. Receiver lifetime and cancellation are difficult to test through the current interface.

Solution

Treat Activity resume and system broadcasts as thin Android adapters into one trigger module. Let that module own event normalization, cancellation, and the handoff to the scan module. Preserve the existing Android signals and the current user-visible behavior.

Candidate 04 · shell depth

Carve the Missing-bucket projection out of XMBViewModel

Speculative

Files / modules

  • XMBViewModel.kt — 7,282 lines
  • XMBItemList.kt and game-detail launch guards
  • Missing-game queries, pseudo-platform rows, counts, navigation, and shell state

Problem

The recent Missing-ROM feature crossed persistence, scan policy, detail launch, pseudo-platform navigation, and rendering. The XMB ViewModel now owns this projection alongside music, video, photo, Discord, achievements, themes, layout editing, and input. Pure helpers are testable, but the call-site locality remains low because the shell module is the integration point for nearly every concern.

Solution

Explore a deep library projection module for All Games, Favorites, Missing, collections, and Memory Card rows. Keep XMB navigation and rendering decisions in the shell, but move database observation, counts, and pseudo-platform projection together. This is deliberately deferred until the scan module shape is settled.
