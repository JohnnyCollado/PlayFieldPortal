ProblemThe confinement policy exists as a comment and a delete loop, not as an enforced interface — so it does not hold.

EvidenceBUNDLED_FILE_ROOTS is used only to delete; the copy that follows is unconstrained:

BUNDLED_FILE_ROOTS.forEach { root -> File(filesDir, root).deleteRecursively() }
staged.forEach { src ->
    val rel  = src.relativeTo(staging).invariantSeparatorsPath
    val dest = File(filesDir, rel)          // <-- rel is never checked against the roots
    dest.parentFile?.mkdirs()
    src.copyTo(dest, overwrite = true)
}

The staging extraction does carry a correct canonical-path zip-slip guard (:352), so nothing escapes the sandbox. But any path under filesDir is writable: datastore/*.preferences_pb (corrupt the live store → crash loop), pfpthemes/, import_plans/, emulator_profiles/custom_profiles.json.

CompoundingA restored profile decides ComponentName, arbitrary extras, and customCommand, then receives grantUriPermission(profile.packageName, romUri, READ). With candidate 4's provider root, that grant can cover any file under /storage/.

SolutionOne module owns the archive: confinement, caps, and profile admissibility. Callers receive already-validated values and cannot opt out.

  • locality: every restore invariant in one module
  • leverage: one interface, three ingestion callers
  • interface shrinks; implementation absorbs the guards
  • tests hit one interface — today BackupManagerTest has nine tests and none for slip, bombs, or non-root paths

Three real call sites justify the seam.

ProblemThe same ingestion policy is reimplemented three times at three quality levels; a fix to one never reaches the others.

EvidenceBackupManager.kt:357 inflates every non-file entry with an uncapped zip.readBytes() and retains it for the whole restore. A games.json of 10 GB of one repeated byte deflates to a few MB — guaranteed OOM. PfpThemeCodec bounds memory per entry but not entry count, so a 64 MB bundle of repeated wallpaper.png entries is an unbounded hang, re-triggered on every PfpThemeStore.scan().

SolutionOne module with the union of the caps. The three readers become callers that supply a name policy, nothing more.

  • leverage: one hardening fix reaches three paths
  • locality: bomb and slip policy in one module
  • the strongest reader becomes the floor, not the exception

After — unrepresentable

ByteCursor

A malformed pointer is a null, not an AIOOBE. Callers cannot forget, because there is nothing to remember.

Problemu32 returns a signed Int, so every caller must independently reject negatives. Two forgot.

val ptr = bytes.u32(ptrOffset)     // 0xFFFFFFFF decodes to -1
if (ptr == 0) break
if (ptr + 12 > bytes.size) break   // -1 + 12 = 11, passes the guard
add(Slot(id = bytes.u16(ptr), ...))  // bytes.u16(-1) throws

Uncaught: PtfThemeImporter.kt:55 calls PtfParser.parse bare, inside a bare viewModelScope.launch. A crafted .ptf picked in Settings ▸ Themes crashes the app. Bounded by the fact that there is no ACTION_VIEW filter for theme files, so no other app can push one in.

Point fixif (ptr < 0 || ptr.toLong() + 12 > bytes.size) break — plus a malformed-pointer case in HostileInputTest. The deepening is what stops the next one.

  • interface makes the defect unrepresentable
  • locality: bounds in one module, not thirteen call sites
  • Gim.kt is desktop-only, so it rides along free

ProblemThe provider can mint a URI for any file under /storage/, but callers only ever need files belonging to a configured ROM source. Nothing enforces the narrower rule.

The provider is correctly exported="false", so no app can query the authority directly — a grant must be minted by PFP. That caps this at Medium on its own. It stops being self-limiting when combined with candidate 1, where the grantee package comes from a restored profile. The repo's own test already imagines this shape: ShortcutIntentSanitizerTest.kt:41 uses content://…/storage_volumes/emulated/0/secret.

SolutionA minter module that resolves a Memory Card's ROM source set and refuses any path outside it — then narrow file_paths.xml to the volume prefixes that survive.

  • uses the domain seam that already exists (ScanSourceResolver)
  • locality: one module answers "may this file be shared"
  • no conflict with ADR-0001 — this consumes ROM sources, it does not survey them

Top recommendation

Give backup restore a trust seam

It is the only path where one user action — restoring a file — reaches both arbitrary filesDir writes and an attacker-chosen ComponentName that then receives a URI grant. Candidates 2 and 4 are its blast radius: the missing caps are on the same reader, and the provider root is what widens the grant. Deepening this one module shrinks all three.

Rotate the ScreenScraper credential first — that is not a refactor and does not wait for this.

Checked and holding — no action

Discord tokens are sealed with a non-exportable Keystore AES-256-GCM key (StrongBox-preferred, random IV, deleteKey on logout); no client secret exists and the RFC 8628 device grant has no interceptable redirect. allowBackup="false" plus the data-extraction rules block token exfiltration. Cleartext is denied app-wide with user CAs confined to debug overrides; there is no WebView in the repo. Exported components are exactly three and all intentional — PinShortcutActivity goes through getPinItemRequest, so a forged intent is a no-op. Every PendingIntent is FLAG_IMMUTABLE. ShortcutIntentSanitizer strips all four URI-grant flags and pins to a resolved component, re-applied at launch as defense in depth. No @RawQuery or interpolated SQL anywhere. The .pfptheme format is not extracted by entry name at all — icons must match a 58-key registry — so zip-slip does not apply to it. Debug surfaces are confined to the debug source set.

Not covered

The vendored Discord AAR was read at manifest level only, not decompiled; it exports AuthenticationActivity with no permission and is the sole declarant of RECORD_AUDIO and three other permissions, which is worth its own pass. Merged manifests from AndroidX/Hilt/Coil were not reviewed. The studio/ desktop companion was out of scope. Nothing was exercised on-device — there is no androidTest source set in the repo.
