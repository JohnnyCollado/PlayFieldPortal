Blockers introduced by this branch 2 findings

Both surfaced from compiler warnings on a clean rebuild. Both trace to the same assumption in the action-vocabulary collapse.

Layout-adjust overlay lost its controller path to the slider toggle

Regression Verified

Phase 0 collapsed BUTTON_Y and LONG_PRESS into OPEN_CONTEXT_MENU on the premise that they always meant the same thing. In 14 of 15 call sites they did. In this one they did not: BUTTON_Y reset the adjustment while LONG_PRESS toggled the sliders. Both now match the first branch, so the second is unreachable.

feature-xmb/.../viewmodel/XMBViewModel.kt:4168 OPEN_CONTEXT_MENU -> resetXmbLayoutAdjust() feature-xmb/.../viewmodel/XMBViewModel.kt:4169 OPEN_CONTEXT_MENU -> toggleXmbLayoutSliders() ← dead before (128b4bc): BUTTON_Y -> resetXmbLayoutAdjust() LONG_PRESS -> toggleXmbLayoutSliders()

Not a total loss of function — XMBShell.kt:219 still reaches toggleXmbLayoutSliders through the on-screen touch control, so only the controller route is gone. It needs its own action (the honest fix) rather than a re-pairing, since the two behaviours are genuinely distinct.

Redundant duplicate branch in the App Drawer dispatcher

Cleanup Verified

Same collapse, benign outcome. The original had LONG_PRESS and BUTTON_Y both calling openAppMenuForSelected() from two branches; they merged into two identical branches. No behaviour change — the second is simply unreachable and should be deleted.

Toolchain: one chain, four flags, a hard expiry AGP 10

The most consequential finding in the repo. Four separate gradle.properties entries look independent but form a single dependency chain, and AGP names the exit itself.

android.builtInKotlin=false Opts out of AGP's built-in Kotlin support
→
kotlin-android plugin Used instead — and it calls the legacy variant API
→
applicationVariants
testVariants Legacy API, off by default in AGP 9
→
android.newDsl=false Required to re-enable it — and it is also what keeps kotlinOptions {} compiling in 16 modules

AGP's own diagnostic states the reason and the fix: “The 'kotlin-android' plugin is currently calling this deprecated API. Please migrate this project to built-in kotlin.” Every link is removed in AGP 10, so this is dated debt, not open-ended. Migrating builtInKotlin is the head of the chain — the kotlinOptions → compilerOptions rewrite across 16 build scripts follows from it rather than standing alone.

Three more AGP 9 escape hatches set to legacy behaviour

Deprecated Verified

Beyond the chain above, gradle.properties pins four further compatibility flags back to pre-AGP-9 defaults. Each is individually reported as deprecated on a --warning-mode=all build.

android.enableAppCompileTimeRClass=false android.r8.optimizedResourceShrinking=false android.usesSdkInManifest.disallowed=false android.sdk.defaultTargetSdkToCompileSdkIfUnset=false

r8.optimizedResourceShrinking=false is not free-standing: it is load-bearing for the Resources.getIdentifier lookup in XMBItemList.kt:1229, which resolves sysicon_* drawables by string name. Optimised shrinking would strip those drawables, since nothing references them statically. Fixing the lookup and the flag is one job, not two.

KSP forced to the legacy KSP1 implementation

Config conflict Verified

The catalog pins a KSP2-generation artifact while gradle.properties forces the old implementation. Room and Hilt codegen both run through this.

libs.versions.toml:10 ksp = "2.2.10-2.0.2" ← KSP2 generation gradle.properties:11 ksp.useKSP2=false ← forces KSP1

It builds today, so this is not urgent. But the pairing is almost certainly a leftover workaround, and whatever it was working around is worth re-testing before it becomes load-bearing knowledge nobody has.

Kotlin 2.2 practice & deprecated APIs 10 findings

Ordered by consequence, not by count. The first three are correctness; the rest are hygiene with real but bounded cost.

Disk read and JSON parse on the main thread during game launch

Correctness Verified

getProfilesForPlatform() is a plain non-suspend function that calls loadPersistedProfiles() → file.readText() plus a decodeFromString. Its callers sit inside viewModelScope.launch { }, which is Dispatchers.Main.immediate — so the file read happens on the UI thread every time a game is launched.

feature-launcher/.../EmulatorProfileRepository.kt:34,36,48 non-suspend, reads disk feature-xmb/.../XMBViewModel.kt:6877 launchGameDirectly() — viewModelScope feature-xmb/.../XMBViewModel.kt:5194 feature-settings/.../LibraryManagerViewModel.kt:460

Nothing in the signature warns a caller that it blocks. The sibling suspend functions in the same class also omit withContext(Dispatchers.IO) — they are safe today only because PFPApplication.appScope happens to be Dispatchers.IO, which is a coincidence of the call site rather than a property of the repository.

catch (e: Exception) swallowing cancellation inside coroutines

Structured concurrency Scan · spot-checked

Roughly a dozen sites catch broad Exception inside suspend or withContext bodies, converting a cancelled scope into a business-level failure result instead of letting it propagate.

EmulatorProfileRepository.kt:91,114,125,137 XmbThemeLoader.kt:59,74,137 IgdbApi.kt:86,100,117 InstalledAppRepository.kt:99 LibraryScanner.kt (3 sites)

The codebase already knows the correct shape — DiscordAuthRepository, RaRemoteDataSource and the workers all rethrow CancellationException explicitly. These sites are drift from an established local convention, which makes them cheap to fix and easy to justify.

Kotlin 2.2 annotation use-site target migration — ~25 warnings

Kotlin 2.2 Verified

Every Hilt-injected ViewModel and several other classes emit “This annotation is currently applied to the value parameter only, but in the future it will also be applied to field.” This is the Kotlin 2.2 change to default annotation use-site targets on constructor properties.

It is the single most frequent warning in the build and is specific to the 2.2 upgrade. Resolve it project-wide with the -Xannotation-default-target compiler flag rather than annotating ~25 sites by hand.

All feature-settings ViewModels · XMBViewModel · GameDetailViewModel ArtworkStudioViewModel · PhotoViewerViewModel · VideoDetailViewModel MusicPlayerController · MusicPlaybackService · ThemeRepository · XmbThemeLoader · PttOverlayManager

collectAsState() at 33 screen entry points — and the doc that teaches it

Compose Verified

33 uses of collectAsState() against 16 of collectAsStateWithLifecycle(). On a launcher that is the resident home app, the non-lifecycle variant keeps collecting while backgrounded.

The root cause is documented, not accidental. The canonical “how to structure a screen in this codebase” example teaches the wrong call:

core-ui/.../preview/PfpPreviewWrapper.kt:30 val state by viewModel.uiState.collectAsState()

This is the highest-leverage item in the section. Fixing that one KDoc block stops the pattern reproducing; the 33 call sites are then a mechanical sweep rather than a recurring drift. lifecycle-runtime-compose is already on every module's classpath.

Orphaned version-catalog pin

Dead Verified

compose-compiler = "1.5.14" at libs.versions.toml:12 is referenced by no version.ref, no composeOptions, and no kotlinCompilerExtensionVersion. Under Kotlin 2.x the Compose compiler ships with the kotlin-compose plugin. The art provenance rules live outside the repo

Risk Verified

Controller_Helper_Icon_Mapping.md — which pack variant each of the 72 drawables came from, the Buttons Solid vs Buttons Full Solid distinction, and the Pro D-Pad rule — exists only in your Downloads folder. The repo preserves it as a comment header in ControllerButtonGlyph.kt, which is better than nothing but omits the per-file source paths.

That distinction is not recoverable by inspection: the two variants are byte-identical for unlettered art and differ only on lettered buttons. Getting it wrong again would produce a subtly mismatched footer that no test can catch. Committing the mapping doc to docs/ is a two-minute hedge against redoing the audit that produced it.

No static analysis, and no UI verification of this branch

Gap

The repo has no ktlint, detekt, or Android Lint configuration. Given that both blockers in this report came from compiler warnings that a green build hid, the cheapest available guard is failing CI on new warnings in the touched modules — not adding a new tool.

Three modules have no test source set at all: :app, :discord:discord-native, :feature:feature-social. Worth noting that ProvideControllerPrompts — the Hilt entry point wiring the whole prompt system — lives in :app and is therefore exercised by nothing in CI.
